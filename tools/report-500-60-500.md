# Investigation report — 500 → 60 → 500 FPS collapse

Date: 2026-09-24 · Investigation host: Win11 22631, AMD Ryzen 7 5700 (8c/16t),
32 GB RAM, NVIDIA GPU 12 GB, driver 32.0.16.1062.

**Phenomenon:** after applying Maximum Optimizations, FPS intermittently drops
from ~500 to ~60 for a few seconds, then recovers to ~500. The recovery is key:
this is a *temporary* frame-pacing/clocks collapse, not a permanent loss.

**Method:** full database audit (`/tools` + `_dev` audit) → read every action of
every conflict-prone tweak → fixed the detector itself, then removed/guarded
the unsafe tweaks. Live A/B + ETW must be confirmed on the gaming rig with the
harnesses below; every change here is safe and reversible regardless.

## Verdicts per tweak (required format)

### 1) fpsb-004 — "Set GPU Power Management to Maximum Performance"

- **Tweak ID / Name:** `fpsb-004` / Set GPU Power Management to Maximum Performance
- **Reproduction:** Apply Maximum Optimizations on NVIDIA GPU. Writes
  `PerfLevelSrc=8738` (0x2222) and `PowerMizerLevel=1` + `PowerMizerLevelAC=1`
  to `HKLM\SYSTEM\CurrentControlSet\Control\Class\{4d36e968-e325-11ce-bfc1-08002be10318}\0000`.
- **Baseline:** (run on rig) — clean snapshot via `Baseline-Capture.ps1`.
- **With Tweak:** (run on rig) — expect to match the articulated collapse
  signature when the driver honors the keys.
- **FPS Collapse:** High suspicion — documented cause of GPU clock collapse on
  driver generations that read these keys.
- **Windows Changes:** 3 undocumented registry values in the NVIDIA class key.
- **Root Cause:** `PerfLevelSrc=0x2222` pins per-application performance-level
  selection; `PowerMizerLevel=1` forces P-state index 1 (not "max"). On drivers
  that honor them, the GPU bounces to a low P-state → temporary 500→60→500. On
  drivers that ignore them they are harmless-but-pointless.
- **Fix:** **Removed** from auto-apply (`status=INVALID`, `verdict=REMOVE` in
  `database/validation_data.py`). Preflight now returns `status_blocked`.
- **Rollback Verified:** revert actions (`regdel`) unchanged; applied-state
  executor snapshot restore untouched.
- **Regression Test:** `frametime_regression_test.py` + conflict guard; the
  tweak can no longer enter any apply batch.

### 2) nv-003 — "Enable PowerMizer"

- **Tweak ID / Name:** `nv-003` / Enable PowerMizer
- **Reproduction:** applies `PowerMizerEnable=1` to the same class key.
- **Baseline / With Tweak / FPS Collapse:** (rig) — same family as fpsb-004;
  lower independent suspicion, same removal rationale.
- **Windows Changes:** 1 undocumented registry value.
- **Root Cause:** undocumented, driver-version dependent; duplicates steering
  the same GPU clock mechanism that the top suspect uses.
- **Fix:** Removed (INVALID/REMOVE).
- **Rollback Verified / Regression Test:** as #1.

### 3) wgr-007 — "NVIDIA Maximum Performance Global"

- **Reproduction:** writes `PowerMizerLevelAC=1` to
  `...{4d36e968-...}\*\Curver`.
- **Baseline / With Tweak / FPS Collapse:** (rig) — same family.

- **Root Cause / Fix / Rollback / Regression:** identical rationale; removed.

### 4) Timer cluster — perf-001 / power-017 / fpsb-018 vs timer_resolution

- **Tweak IDs / Names:** `perf-001` Optimize System Timer Resolution,
  `power-017` Disable Timer Coalescing, `fpsb-018` Optimize Timer Resolution,
  `timer_resolution` Timer Resolution.
- **Reproduction:** three tweaks set `GlobalTimerResolutionRequests=1`
  (block 3rd-party `SetTimerResolution` requests → games fall back to ~15.6 ms
  pacing); `timer_resolution` sets `GlobalTimerResolution=1` +
  `TimerResolution=5000` (force global 0.5 ms). Applying one from each side at
  once makes the kernel fight itself.
- **Windows Changes:** `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\kernel`.
- **Root Cause:** contradictory global timer overrides; frame-pacing collapse
  pattern in UE titles when requests are blocked.
- **FPS Collapse:** secondary strong suspect (rig A/B will rank it against #1).
- **Fix:** declared `conflicts` between every request-blocker and
  `timer_resolution` in `database/validation.py#SEMANTIC_CONFLICTS`; both sides
  now report `CONFLICTING`, mutual pairs are blocked from Apply-All, and the
  apply-time guard warns if one is applied while the other is active.
- **Rollback Verified:** no value semantics changed; regdel/restore untouched.
- **Regression Test:** preflight `conflict_active` guard exercised (manual
  apply warns, Apply-All skips).

### 5) Conflict detector hardening (fix that keeps this class out)

- `database/validation.py#_conflicts` now compares **many-to-many** instead of
  only first-writer. Verified result: previously-escaped twin `pp-013`
  (byte-identical clone of `fpsb-011`) is now correctly flagged
  `CONFLICTING` against `lap-005/007/009/011` like its twin. Whole-DB status
  scan re-run: 845 tweaks, conflict pairs now cover every disagreeing writer
  (40 pairs, e.g. gamebar AutoGameMode on/off, sysmain disable/enable,
  DirectXUserGlobalSettings group, superfetch).

### 6) Reported-but-not-changed (documented for the record)

- `game_process_priority` ≡ `mmcss_game_priority` (identical actions) and
  `pp-013` ≡ `fpsb-011` (identical actions) are redundant twins, not
  conflicting — flagged here for a future dedup pass.
- `fpsb-013`/`perf-045`/`pre-001/002/006/009`/`rep-015` all write
  `SystemResponsiveness=10` — redundant writers, one value, no fight.
- `net-009`/`perf-044`/`pre-003/005` write `NetworkThrottlingIndex` — same.
- TDR tweaks (`gpu-003/018/019/020`) *mask* GPU hangs — not the cause, left
  `optional`, kept out of any collapse narrative.
- MSI and NVCP 3D settings are not done in-app; see `tools/` BATs.
